Prayer Request Notifications

Deployment guide for email notifications and admin deletion features

What you're adding:

  • Email notifications — When a visitor submits a prayer request, the church receives an email
  • Admin delete — Admins can remove prayer and ministry-join requests from the dashboard
  • Notification settings — Control email notifications from the admin panel (on/off + recipient address)

Prerequisites

Before you start, confirm these are complete:

  1. Migrations 004 and 005 have been run in your Supabase project
  2. You have an admin user seeded via seed_admin.sql
  3. You can log in to the admin dashboard and save settings
  4. You have a Resend.com account (free tier supports 100 emails/day, 3,000/month)

Step 1: Database Schema

Migration 006 adds the notification settings table and the deletion policy.

What it does

  • Creates notification_settings — a singleton, admin-only table
  • Adds prayer_requests.notified_at to prevent double-sends
  • Confirms the admin DELETE policy (added in 004, re-created for idempotency)
  • Tightens the visitor INSERT grant to column-scoped (they cannot forge notified_at)

Run in Supabase Dashboard → SQL Editor

-- File: supabase/006_prayer_notifications.sql
-- Already created in your project directory
-- Run the whole file once
⚠ Why a separate table?
church_settings has a "Public can view settings" policy — it feeds the footer, contact, and give pages. Putting the notification recipient there would publish that address to anyone with the anon key (visible in page source). notification_settings is admin-only.

Step 2: Email Service Setup

2.1 Create Resend Account

  1. Go to resend.com/signup
  2. Create an account (free tier: 100 emails/day, 3,000/month)
  3. Verify your domain OR use Resend's sandbox domain for testing
    • Sandbox: works immediately, delivers only to your account email
    • Custom domain: requires DNS records (TXT for verification, MX/TXT/CNAME for sending)
  4. Navigate to API Keys → Create API Key
  5. Name it "Hills of Glory Notifications", select "Full Access"
  6. Copy the key — it's shown once

2.2 Deploy the Edge Function

The function is already written at:

supabase/functions/notify-prayer-request/index.ts

Install the Supabase CLI if you haven't:

npm install -g supabase

Link your project:

supabase login
supabase link --project-ref YOUR_PROJECT_REF

Find YOUR_PROJECT_REF

Supabase Dashboard → Settings → General → Reference ID

Set the secrets:

# The Resend API key you just copied
supabase secrets set RESEND_API_KEY=re_...

# A long random string — you'll use this when configuring the webhook
supabase secrets set NOTIFY_WEBHOOK_SECRET=$(openssl rand -hex 32)

# The verified sender address
# Sandbox: "onboarding@resend.dev"
# Custom domain: "noreply@hillsofglory.org"
supabase secrets set NOTIFY_FROM_EMAIL=noreply@hillsofglory.org

Deploy:

cd supabase/functions
supabase functions deploy notify-prayer-request --no-verify-jwt

--no-verify-jwt is required — the webhook is not an authenticated user. The shared secret you set above is what authenticates the caller.

✓ Function deployed
Copy the function URL from the output — you'll need it for the webhook.

2.3 Configure the Database Webhook

Supabase Dashboard → Database → Webhooks → Create a new hook

Field Value
Name Notify prayer request
Table prayer_requests
Events Insert ✓ (only)
Type HTTP Request
Method POST
URL https://YOUR_PROJECT_REF.supabase.co/functions/v1/notify-prayer-request
HTTP Headers x-webhook-secret → the value you generated with openssl rand -hex 32
(Retrieve it: supabase secrets list)

Save the webhook.

⚠ The x-webhook-secret header is critical
Without it, the function is a public email relay. The function checks this header on every request and rejects calls that don't match.

2.4 Test the Integration

Option A: Submit via the contact page

  1. Open your website → Contact page
  2. Fill in the prayer request form and submit
  3. Check the recipient email inbox (sandbox sends only to your Resend account email)

Option B: Insert directly in SQL Editor

INSERT INTO public.prayer_requests (visitor_name, request_text)
VALUES ('Test User', 'This is a test request to verify email delivery.');

What to check:

  • Email arrives within 10 seconds
  • Subject: "Prayer request from Test User"
  • Body contains the request text, properly escaped
  • The row's notified_at column is stamped (query it or check in the Table Editor)

Troubleshooting:

  • No email + notified_at still NULL: Check the function logs (Dashboard → Edge Functions → notify-prayer-request → Logs)
  • "Unauthorized" in logs: The webhook secret doesn't match
  • "Mailer not configured": RESEND_API_KEY or NOTIFY_FROM_EMAIL not set
  • Resend rejects: Check the sender is verified (or use the sandbox domain)

Step 5: Complete the JavaScript

The notification settings save handler needs to be added to admin/js/admin-cms.js.

Insert this after the valueOf function (around line 458):

  // --- Notification Settings Form ---
  const notifyForm = document.getElementById('notifyForm');
  if (notifyForm) {
    notifyForm.addEventListener('submit', async function (e) {
      e.preventDefault();

      const submitBtn = notifyForm.querySelector('[type="submit"]');
      if (submitBtn) submitBtn.disabled = true;

      const emailEl = document.getElementById('notifyEmail');
      const enabledEl = document.getElementById('notifyEnabled');

      const payload = {
        prayer_notify_email: emailEl ? emailEl.value.trim() : '',
        prayer_notify_enabled: enabledEl ? enabledEl.checked : true,
      };

      const { data, error } = await supabase
        .from('notification_settings')
        .upsert(Object.assign({ id: SETTINGS_ID }, payload))
        .select('id')
        .single();

      if (submitBtn) submitBtn.disabled = false;

      if (error) {
        showToast(error.code === '42501'
          ? 'Permission denied — your account needs role = admin.'
          : 'Could not save notification settings.', 'error');
        console.error(error);
      } else {
        showToast('Notification settings saved!', 'success');
        loadNotificationSettings();
      }
    });
  }

  • Run SELECT id, visitor_name, notified_at FROM prayer_requests ORDER BY date_submitted DESC LIMIT 5; — notified_at column exists

✓ Admin panel → Notifications section

  • Form loads with the current settings
  • Saving updates the row and shows "Notification settings saved!"
  • Unchecking "Send email" and saving turns notifications off

✓ Admin panel → Requests section

  • Prayer requests list with Delete buttons
  • Clicking Delete asks for confirmation, then removes the row
  • Tab switches between Prayer / Ministry Join requests
  • Emailed requests show a badge

✓ Email delivery

  • Submit a prayer request from the contact page
  • Email arrives within 10 seconds
  • Visitor-supplied text is escaped (try submitting <b>bold</b> — it should render as literal text, not formatted)
  • The request row in the admin panel shows the "Emailed" badge

✓ Idempotency

  • Webhook replays don't send duplicates (re-trigger the webhook in Dashboard → Database → Webhooks → click the row → Send test event — only one email arrives even if you fire it 5 times)

Backfilling Unsent Notifications

If you had prayer requests submitted before the webhook was configured, their notified_at is NULL and no email was sent.

To send emails for old requests:

-- List unsent requests
SELECT id, visitor_name, date_submitted
FROM prayer_requests
WHERE notified_at IS NULL
ORDER BY date_submitted;

-- Trigger the function manually for each one by calling the webhook URL
-- (use curl, Postman, or the Supabase Dashboard's "Send test event")

The function's idempotency check prevents double-sends: once notified_at is stamped, re-invoking the webhook for that row does nothing.

Cost & Limits

Resend Free Tier

  • 100 emails/day
  • 3,000 emails/month
  • 1 custom domain

If your church expects more than ~95 prayer requests per day, consider the Pro plan ($20/month for 50,000 emails).

Supabase Edge Functions

  • Free tier: 500,000 invocations/month
  • 2M CPU-seconds/month

The notify function uses ~100ms per call, so even at the free tier you can handle 20M prayer requests/month before hitting the CPU limit.
